# 검토 사항과 보류 아이디어의 구현 가능성

현재 1단계 코드와 임시 실험을 기준으로 검토합니다. 이 문서는 구현 완료 목록이 아니라 가능 조건과 추가 작업의 기록입니다.

## 검토 사항

### pytest 실행 감지와 결과 수집

구현 가능합니다. 현재는 `-p pytest_menu_helper.plugin --menu-events PATH`를 지정해야 수집하며, 최종 집계와 화면 표시는 아직 없습니다.

### 다른 터미널 실행의 자동 감지

조건부로 가능합니다. 사용 중인 Python 환경에 플러그인을 설치하고 pytest의 자동 로드가 허용되어 있어야 합니다. 독립 PTY 실험에서는 설치된 플러그인의 자동 로드를 확인했지만, 현재 저장소 패키지에는 아직 `pytest11` 자동 로드 등록이 없습니다.

이미 열린 터미널에 앱의 환경변수가 전파된다고 가정하지 않고, 플러그인과 앱이 공통 로컬 설정에서 기록 위치를 찾도록 추가 설계해야 합니다. 실제 Terminal.app, 플러그인 미설치 환경과 자동 로드 비활성화 환경을 대조하는 검증도 남아 있습니다.

### 테스트 없음과 중단 등 예외 상태

구현 가능합니다. 현재 코드로 다시 실행한 결과는 다음과 같습니다.

- skip만 있는 실행: 종료 코드 0, `call` 단계 `skipped` 기록
- 테스트 없음: 종료 코드 5, 시작·종료만 기록
- 테스트 본문에서 `KeyboardInterrupt` 발생: 종료 코드 2, setup 이후 실행 종료 기록

수집 오류 역시 종료 코드 2일 수 있으므로 `collection_error`와 함께 해석해야 합니다. 현재는 별도 중단 사유 이벤트가 없으므로 세부 원인을 모두 구분할 수 없습니다. 강제 종료나 기록 실패로 종료 이벤트가 빠지면 성공이 아니라 미완료로 표시해야 합니다. 앱이 실행한 프로세스의 생존 여부와 외부 실행의 상태 확인 방법도 후속 구현 대상입니다.

실험 환경은 Python 3.13.9, pytest 8.4.2입니다. Python 3.12와 macOS 전체 앱 동작을 검증한 결과는 아닙니다.

엄격한 xpass는 `failed`로 기록되지만 명시적인 xpass 필드가 없습니다. 별도 건수로 구분하려면 추가 설계가 필요합니다. setup·teardown 실패도 call 단계와 함께 집계해야 합니다.

## 추가 구현 목표로 전환한 아이디어

### 이전 실행 대비 새 실패와 회복

구현 가능합니다. 현재 JSONL로 두 실행을 비교한 임시 실험에서 동일 테스트의 `passed → failed`와 `failed → passed`를 확인했습니다.

추가할 기능은 실행 이력 저장과 테스트별 최종 판정 집계입니다. 프로젝트 정체성과 pytest rootdir을 고정하고 `(프로젝트, nodeid)`로 비교해야 합니다. 테스트 이름 변경은 같은 테스트라고 자동 추정하지 않습니다.

부분 실행에서 빠진 테스트를 회복이나 삭제로 간주하면 안 됩니다. 완료된 두 실행에서 공통으로 관측한 테스트만 우선 비교하고, 없는 테스트는 미실행/비교 불가로 표시하는 범위를 권합니다. 현재 이벤트에는 선택 옵션과 전체 수집 테스트 목록이 없어 완전한 실행 범위 비교에는 필드 추가가 필요합니다.

### 실패 위치를 에디터에서 열기

구현 가능합니다. 현재 이벤트의 절대 경로와 1부터 시작하는 줄 번호를 사용할 수 있습니다.

- VS Code: `code --goto <파일>:<줄>`
- PyCharm: `pycharm --line <줄> <파일>`

공식 명령 형식과 로컬 VS Code 실행 파일 존재를 확인했습니다. 실제 앱 실행과 커서 이동은 아직 검증하지 않았습니다. 먼저 VS Code 하나를 지원하고 다른 에디터는 후속으로 추가하는 범위를 권합니다.

macOS 앱의 PATH가 터미널과 다를 수 있으므로 실행 파일 위치를 확인해야 합니다. 파일 존재 여부와 유효한 줄 번호를 검사하고, 공백이 포함된 경로는 셸 문자열 결합 대신 인수 배열로 전달합니다. 실패 위치가 없으면 이동 불가 안내나 명시적인 테스트 정의 위치 대체 동작이 필요합니다.

근거: [VS Code CLI](https://code.visualstudio.com/docs/configure/command-line), [PyCharm CLI](https://www.jetbrains.com/help/pycharm/opening-files-from-command-line.html).

### 프로젝트 맵과 실행 경로 재생

구현 범위를 나누어야 합니다.

- 파일·테스트 맵: 구현 가능합니다. Python AST 실험으로 샘플 함수와 테스트 정의를 추출했습니다. 파일과 테스트를 노드로 두고 결과·보고 순서에 따라 캐릭터를 움직이는 방식부터 시작할 수 있습니다.
- 실제 함수 호출 경로: 별도 추적기를 추가해야 합니다. 현재 이벤트에는 함수 호출 간선과 진입 시점이 없으므로 이를 복원할 수 없습니다. 현재 report 시각은 실행 시작 시각도 아닙니다.

FastAPI TestClient 실험에서는 `sys.settrace`만으로 worker thread의 endpoint 호출을 잡지 못했고, `threading.settrace`를 추가했을 때 endpoint 호출 1건을 포착했습니다. 이는 제한된 동기 endpoint 실험이며 모든 실행 경로의 검증은 아닙니다.

실제 경로 재생에는 테스트와 호출의 연결, 기존 스레드, async 작업 간 교차, subprocess, 호출·반환 순서, 성능 영향, 다른 추적기와의 충돌을 추가 검증해야 합니다. 정적 맵을 실제 실행 경로라고 표시하면 안 됩니다.

## 권장 추가 순서

1. 기존 2단계 집계·중단·미완료 처리를 기반으로 기본 앱을 완성합니다.
2. 결과 화면 이후 VS Code 위치 이동을 추가합니다.
3. 완료된 실행 이력을 저장하고 새 실패·회복 비교를 추가합니다.
4. 기본 기능 이후 파일·테스트 맵을 추가합니다.
5. 실제 함수 경로 추적은 사용자가 활성화하는 기능으로 검증하고 추가합니다.

모든 아이디어를 최종 목표에 포함합니다. 기본 기능을 먼저 완성하고 구현 계획 9~13단계에서 확장합니다. 실제 함수 경로 추적은 지원 범위를 검증하며 추가하고, 전체 구현 기간은 아직 확정하지 않습니다. 조건부 자동 감지와 예외 처리 검증은 기존 구현 계획의 필수 단계로 유지합니다.

## 다중 가상환경 지원 목표 추가

여러 가상환경의 동시 테스트와 환경별 결과 비교를 9단계 목표로 추가했습니다. 현재 실행 ID는 있지만 환경 식별 정보와 동시 실행 집계가 없으므로 아직 지원되는 기능은 아닙니다.

환경별 인터프리터·플러그인 확인, 실행별 파일 분리, 환경과 실행을 구분한 집계·UI, 공유 테스트 자원 충돌 처리가 필요합니다. 서로 다른 환경을 시간상 새 실패·회복으로 잘못 비교하지 않도록 이력 기준도 확장합니다. 실제 가상환경 2개를 동시에 실행해 결과가 섞이지 않는지 확인하는 것을 완료 기준으로 두며, 현재는 이 검증을 수행하지 않았습니다.
