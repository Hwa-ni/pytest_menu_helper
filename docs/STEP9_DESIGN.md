# 9단계 설계: 여러 가상환경 동시 실행과 환경별 비교

상태: **완료(2026-11-18).** 구현, 자동·통합 검증, 사용자 화면 확인을 마쳤다. 7절 결정 2는 2026-11-17 사용자 결정, 나머지(1·3·4·5)는 2026-11-18 사용자가 구현을 지시해 추천안으로 확정했다. 구현하며 정한 세부(1개짜리 묶음, [모두 중지] 범위 등)와 검증 결과는 `docs/APP.md`의 "9단계" 절에 있다.

범위 원본은 `IMPLEMENTATION_PLAN.md`의 "9. 다중 가상환경 동시 테스트와 환경별 결과 비교"다.

완료 기준: 실제 가상환경 2개에서 같은 테스트를 동시에 실행해 한 환경만 실패하는 사례를 재현한다. 결과 파일·집계·알림이 섞이지 않고 환경과 실행을 정확히 표시하며, 한 환경 중단과 플러그인 누락도 독립 처리한다. 환경을 바꿔 실행한 결과를 기존 환경의 시간상 회복으로 오판하지 않는다. pytest-xdist(한 pytest 안의 병렬화)는 범위 밖이다.

## 1. 지금 있는 것과 없는 것

이미 있는 것(코드로 확인):

- 이벤트 파일이 실행마다 따로 생긴다(`events/<run_id>.jsonl`). 로그도 실행마다 따로다. 파일 단위로는 이미 섞이지 않는다.
- session_start에 환경 id, prefix, python_path, python_version, pytest·플러그인 버전이 들어간다(`plugin.py` `_environment`). 환경은 이름·버전이 아니라 prefix로 구분한다.
- 결과·소요 시간·실행 ID·출처는 모두 환경 id를 키로 둔다(`RunSnapshot.results/elapsed/runIDs/sources`).
- 터미널 감지(`ExternalRunWatcher`)는 여러 실행을 동시에 추적한다(`ExternalSnapshot.active` 배열).
- 팝오버는 환경별 행이고, 알림 제목에 `프로젝트 / 환경`이 들어간다.
- 가상환경 `~/.venvs/pmh-3.9`(pytest 8.4.2), `pmh-3.12`·`pmh-3.13`(pytest 9.2.0) 모두 플러그인 0.3.0과 FastAPI가 설치돼 있다. 이 Mac은 10코어다.

없는 것(이번 단계에서 만들 것):

- **앱 실행이 하나뿐이다.** `RunSnapshot.active: ActiveRun?`(RunModels.swift:279), `StartResult.alreadyRunning`(RunModels.swift:326), 두 번째 실행 거부(RunController.swift:89). 중지 `stop()`도 환경을 받지 않고, `context`·`runningProcess`도 하나씩이다.
- 다른 환경이 돌면 ▶가 꺼진다("다른 환경이 실행 중입니다(동시에 1건만 실행)", ResultPresentation.swift:317).
- 환경끼리 결과를 비교하는 화면이 없다.
- 한 환경에서만 실패하는 샘플이 없다.
- 캐릭터는 "가장 나중에 시작한 실행 하나"를, 알림은 "실행 하나에 1건"을 따른다(7·8단계 규칙).

## 2. 실행 다중화 (PMHCore)

### 2.1 상태 모양

- `RunSnapshot.active: ActiveRun?`를 `actives: [String: ActiveRun]`(환경 id 키)로 바꾼다. **한 환경에서는 동시에 1건만** 허용한다. 같은 가상환경을 두 번 동시에 돌리면 결과 키가 겹치고 비교 의미도 없다.
- `ActiveRun`에 `batchID: String?`를 더한다. [모두 실행]으로 함께 시작한 실행은 같은 묶음 ID를 가진다. 낱개 ▶는 nil.
- 끝난 결과에도 묶음 ID를 남긴다(`batchIDs: [String: String]`, 환경 id 키). 캐릭터·알림·비교가 "같이 돌린 결과"를 묶는 기준이다.
- 묶음 상태 `batches: [String: BatchState]`: 묶음에 든 환경 id 목록, 시작 시각, 다 끝났는지. 모든 환경의 결과가 정해지면 끝난 것으로 본다.

### 2.2 RunController

- `context`와 `runningProcess`를 실행 ID 키 사전으로 바꾼다. 잠금과 work 큐 규칙은 그대로다(work 큐 하나가 여러 실행의 타이머를 돌린다. 각 작업이 짧아 충분하다. 집계 호출(최대 30초)이 다른 실행의 진행 갱신을 막는 문제는 아래 "위험" 참고).
- `start(envID:...)` 결과: `.started(runID)`, `.alreadyRunning`(이 환경이 이미 실행 중), `.limitReached`(동시 실행 수 초과).
- `startAll(envs:)`: 묶음 ID를 만들고 환경마다 start. 제한을 넘는 환경은 차례 대기 줄에 둔다(7절 결정 2).
- `stop(envID:)`: 그 환경 실행만 SIGINT → 5초 뒤 SIGKILL. `stopAll()`: 실행 중인 모든 환경에 같은 절차.
- `stopForTermination`: 살아 있는 모든 자식에게 SIGINT를 한꺼번에 보내고, **하나의 마감 시각**(기본 2.5초, 상한 5초)까지 함께 기다린 뒤 남은 것에 SIGKILL. 환경마다 따로 기다리면 3개일 때 종료가 최대 16초 멈춘다.
- 한 실행의 실패·중지·launchFailed는 그 환경 키만 바꾼다. 다른 실행의 Context·타이머·프로세스에는 손대지 않는다. 이를 단위 테스트로 고정한다.
- 오래된 파일 정리(`FileCleaner.pruneAll`)는 실행 중인 모든 실행 ID를 보호한다. 지금은 방금 끝난 실행 하나만 보호해서, 동시 실행이면 돌고 있는 다른 실행의 파일을 지울 수 있다.

### 2.3 동시 실행 수

- 최대 **10**(7절 결정 2, 2026-11-17 사용자 결정). 이 Mac의 코어 수(10)와 같다. 상수 하나(`RunController.maxConcurrentRuns`)로 둔다.
- 측정은 제한값을 정하려는 것이 아니라 **10개에서 버티는지 확인**하려는 것이다. `slow_demo`(5개, 약 10초)를 1·3·10개 동시로 돌려 총 시간, 환경별 시간, 앱 진행 갱신 지연(0.25초 주기가 지켜지는지), 앱 종료 정리 시간을 잰다. 결과는 `docs/APP.md` 9단계 절에 적는다.
- 지금 플러그인이 깔린 가상환경은 3개(3.9·3.12·3.13)뿐이다. 10개 측정용 환경은 `~/.venvs/pmh-load-01`~`10`처럼 uv로 저장소 밖에 만들고, 측정 뒤 지울지 묻는다. 같은 Python을 다른 환경 id로 10번 등록하는 방법도 있지만, 터미널 감지가 prefix로 환경을 찾으므로 실제 환경을 따로 만드는 쪽이 정확하다.
- 터미널 실행은 앱이 띄우지 않았으므로 제한에 세지 않는다.

### 2.4 pmh-run

자동 통합 검증을 화면 없이 하려고 `pmh-run`에 여러 환경 옵션을 더한다. 예: `pmh-run --env a=~/.venvs/pmh-3.9/bin/python --env b=~/.venvs/pmh-3.13/bin/python examples/multi_env_demo`. 환경별 결과 줄과 비교 요약을 출력한다. `--stop-after <초> --stop-env a`로 한 환경만 중지하는 시험도 한다.

## 3. 화면

### 3.1 팝오버

- 프로젝트 줄에 **[모두 실행]**. 실행 가능한 환경(검사 통과, 플러그인 있음)만 시작한다. 플러그인 누락 환경은 건너뛰고 그 행에 이유가 그대로 보인다(독립 처리). 실행 중이면 같은 자리가 **[모두 중지]**.
- 환경별 ▶·■는 서로 독립이다. 다른 환경이 돌아도 ▶는 켜져 있다. 제한에 걸리면 ▶를 끄고 도움말 "동시 실행은 10개까지입니다".
- 차례를 기다리는 환경 행: "차례 기다림"(회색 진행 바 없음), ■로 대기 취소.
- 환경·프로젝트 제거 막기는 "실행 중인 환경 하나"가 아니라 "실행 중인 환경 집합" 기준으로 바꾼다.

### 3.2 환경 비교 절

선택한 환경의 상세 아래에 "환경 비교" 절을 둔다. 프로젝트에 결과가 있는 환경이 2개 이상일 때만 보인다.

- 행: 테스트 하나(nodeid + 반복 번호). 열: 환경. 칸: 통과·실패·오류·skip·xfail·xpass·미완료·미실행·**없음**(그 환경에서 수집되지 않음)·**수집 오류**(그 파일이 그 환경에서 import 실패).
- 정렬: **결과가 다른 테스트 먼저**, 그다음 모두 같은 테스트는 접어서 "모두 같음 12건"으로 한 줄.
- 없음·미실행·미완료·수집 오류는 **통과로 세지 않는다.** 한 환경은 통과, 다른 환경은 없음이면 "결과가 다름"이다.
- 비교 대상 표시: 열 머리에 환경 이름, Python 버전, 출처(앱·터미널), 끝난 시각. 같은 묶음이면 "함께 실행", 아니면 "따로 실행 · 시작 차이 12분"을 붙인다. 따로 실행한 결과는 코드가 달랐을 수 있다는 뜻이다.
- 실행 조건이 다르면(터미널에서 `-k`, 경로 지정 등 인수가 다름) 비교 표를 그대로 두되 맨 위에 "실행 조건이 달라 일부 테스트가 빠졌을 수 있습니다"를 보인다. 이를 위해 집계기 JSON에 session_start의 실행 인수를 실어 보낸다(지금 Swift 쪽에는 없다).
- 이 비교는 **같은 시점의 환경 간 비교**다. 같은 환경 안의 시간상 변화(새 실패, 회복)는 11단계이며 여기서 만들지 않는다. 결과가 환경 id로만 저장되므로 환경 B 결과가 환경 A의 "회복"으로 보일 경로가 없다. 이를 테스트로 고정한다.

### 3.3 캐릭터 (7단계 규칙 변경)

- 묶음 실행 중: 달리기 + "3개 환경 실행 중"(끝난 수가 있으면 "3개 환경 중 1개 끝남").
- 묶음이 다 끝나면: 하나라도 실패 → 넘어진 포즈 + "1/3 환경 실패". 실패 없이 확인 필요가 있으면 갸웃. 모두 통과면 점프 + "3개 환경 통과".
- 묶음이 아닌 낱개 실행은 지금 규칙 그대로(가장 나중 것 하나).
- 도움말(마우스 올림)에 환경별 한 줄씩: "pmh-3.9 · 실패 1", "pmh-3.13 · 통과".

### 3.4 알림 (8단계 규칙 변경)

- 묶음은 **다 끝난 뒤 요약 1건**. 제목 "3개 환경 중 1개 실패 · fastapi_demo", 본문 "pmh-3.9 실패 1 · pmh-3.12 통과 · pmh-3.13 통과".
- 묶음에 든 실행 ID는 모두 처리한 것으로 넣어, 낱개 알림이 따로 나가지 않게 한다.
- 묶음 안의 일부를 사용자가 ■로 멈췄으면 그 환경은 "중단됨"으로 요약에 넣는다. 모두 멈췄으면 보내지 않는다(8단계 결정 2와 같은 이유).
- 낱개 ▶와 터미널 실행은 지금 규칙 그대로 1건씩.
- 알림을 누르면 팝오버를 열고 그 프로젝트, 실패한 첫 환경, 환경 비교 절을 보인다.

## 4. 공유 자원 점검과 샘플

### 4.1 앱 쪽

| 자원 | 동시 실행 때 | 조치 |
|---|---|---|
| 이벤트·로그 파일 | 실행 ID별 파일 | 그대로. 섞임 검사(`eventsMixed`)도 그대로 |
| 오래된 파일 정리 | 돌고 있는 다른 실행 파일을 지울 수 있음 | 실행 중 ID 전체 보호(2.2) |
| `__pycache__` | 파일 이름에 버전 태그(cpython-39 등) | 문제 없음. 같은 버전 두 환경이면 측정으로 확인 |
| `.pytest_cache` | 여러 pytest가 같은 폴더에 씀 | 측정으로 확인. 깨지면 문서에 적고, 앱이 몰래 끄지는 않는다(사용자 환경 불변 원칙) |

### 4.2 샘플 `examples/multi_env_demo/`

- `test_version.py`: Python 3.9에서만 실패하는 테스트. 예: `zip(..., strict=True)`(3.10부터 지원, 3.9에서는 TypeError). 수집 오류가 아니라 **테스트 실패**가 나도록 함수 안에서 쓴다.
- `test_shared.py`: 공유 자원을 쓰는 바른 예. `tmp_path`, 포트 0 바인딩, 환경마다 다른 SQLite 파일.
- `test_shared_bad.py`는 기본 수집에서 빠지게 두고(`-m conflict` 같은 표식), 고정 파일 이름·고정 포트를 써서 동시 실행 때 충돌이 실제로 나는지 보여 준다. README에 "왜 이렇게 쓰면 안 되는지" 한 단락.
- 각 테스트가 약 1초 걸리게 해 동시 실행이 눈에 보이게 한다.

## 5. 검증 계획

- 단위 테스트(swift-testing):
  1. 두 환경 동시 start, 같은 환경 두 번 start 거절, 제한 초과 대기.
  2. 한 환경 stop·SIGKILL·launchFailed가 다른 환경 상태를 바꾸지 않음.
  3. 정리 함수가 실행 중 ID를 모두 보호.
  4. 비교 표: 없음·미실행·수집 오류가 통과로 세지지 않음, 다른 결과 먼저, 실행 조건 다름 경고.
  5. 환경 B 결과가 환경 A 결과를 바꾸지 않음(회복 오판 없음).
  6. 캐릭터 묶음 문구와 포즈, 알림 요약 1건과 낱개 알림 생략.
  7. stopForTermination이 여러 자식을 하나의 마감 시각 안에 정리.
- 통합(자동, `pmh-run`):
  1. 3.9 + 3.13으로 `multi_env_demo` 동시 실행 → 3.9만 실패 1, 3.13 통과(완료 기준).
  2. 한 환경만 중지 → 그 환경 중단됨, 다른 환경 정상 완료.
  3. `pmh-noplugin` 포함 [모두 실행] → 그 환경만 건너뜀, 나머지 정상.
  4. 이벤트 파일마다 run_id·env 정보가 자기 환경 것만 있는지 검사.
  5. 2.3의 1·3·10개 동시 실행 측정과, 10개 실행 중 앱 종료 때 모든 자식이 상한(약 5.5초) 안에 정리되는지.
- 사용자 화면 확인: [모두 실행]·[모두 중지], 환경별 ▶ 독립, 환경 비교 절, 캐릭터 묶음 문구, 요약 알림 1건.

## 6. 위험

- **집계 호출이 work 큐를 막는다.** 한 실행이 끝나 집계(보통 1초 안, 상한 30초)하는 동안 다른 실행의 진행 갱신이 멈춘다. 측정에서 눈에 띄면 집계를 별도 큐로 옮긴다. 처음부터 옮기지 않는 이유는 상태 변경 순서가 지금 work 큐 하나에 기대고 있어서다.
- **7·8단계 규칙이 바뀐다.** 캐릭터·알림이 묶음 단위가 되면 이전 테스트 일부를 고쳐야 한다. 낱개 실행 규칙은 유지해 바뀌는 범위를 묶음으로 한정한다.
- **`.pytest_cache` 동시 쓰기**가 깨질 수 있다. 측정 전에는 모른다. 10개가 같은 폴더에 쓰면 3개보다 가능성이 크다.
- **10개 동시면 테스트 자체가 느려질 수 있다.** 코어 10개를 pytest 10개가 나눠 쓰고 앱의 work 큐도 10개 타이머를 돌린다. 시간에 민감한 테스트(타임아웃 등)는 동시 실행 때만 실패할 수 있다. 그러면 환경 차이로 보이므로, 측정에서 이런 실패가 나오면 문서에 적는다.
- **"같은 코드" 보장은 못 한다.** 함께 실행한 묶음만 같은 시점의 코드다. 따로 실행한 결과 비교는 시작 차이로 표시만 한다(git 상태 기록은 범위 밖).
